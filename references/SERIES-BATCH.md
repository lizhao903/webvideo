# 系列批量改版 —— 给已完成系列的所有集数做统一结构调整

> **适用场景**：系列已经做完（或做完大半），现在要给**每一集**统一加/改
> 同一个结构性东西——比如给全系列加统一开场品牌章节、统一收尾话术、换一版
> 通用组件。**不是从零做新视频**（那走 Phase 1-5），是对既有多集内容做
> 一次性批量改版。

实战来源：「深度学习入门」33 集系列，先在 1 集上做出样板、用户确认后，
批量套到其余 27 集 app 版 + 28 集 pc 版，过程中踩的坑都在这份文档里。

---

## Part 1 · 核心矛盾：每集能并行，两类资源不能并行

批量改版天然适合"多个 subagent 同时开工，一集一个 agent"——每集是独立
目录，互不干扰，代码层面**可以**大批量并行。但系列生产链路上有两类**全局
单例资源**，多个 agent 同时用会互相冲突：

| 资源 | 冲突表现 | 原因 |
|---|---|---|
| 本地 TTS 进程（index-tts / 类似的本地模型 CLI） | 后合成的把先合成的输出覆盖 / 显存或内存爆 / 合成结果对不上文本 | 模型只能单实例跑，多进程抢同一份权重 |
| dev server 端口 + `start.sh`/`stop.sh` 命名 | agent A 的 Playwright 截图截到了 agent B 项目的画面，验证"通过"实际是错的 | 脚手架的 `start.sh <slug>` 不管 slug 是什么，**pid/log 文件名固定叫 `app`**——第二个 `start.sh` 调用检测到"已经在跑"，直接返回第一个的端口，不会真的为新项目起新服务 |

**后果最隐蔽的是第二条**：如果不知道这个限制，会出现"27 个 subagent 都
各自截图验证说通过了"，但其实它们截的都是同一个（最先起来的那个）项目
的画面——虚假的全绿。

## Part 2 · 正确分工：subagent 只写代码，主控串行收尾

批量改版按下面这条线分工，两类资源冲突就消失了：

```
subagent（可大批量并行，一集一个）
  └─ 只做：新增/修改章节代码 + CSS + narrations.ts
           + npm run extract-narrations（重生成 audio-segments.json）
           + npx tsc --noEmit 自检到 0 error
  └─ 禁止：起 dev server / 跑 Playwright / 跑音频合成命令 / 渲染视频 / git commit

主控（当前 agent，严格串行，一集处理完再下一集）
  └─ 对每一集依次：
       1. 音频合成（本地 TTS，增量模式，只合成新增/改动的段落）
       2. 起 dev server（此时只有它自己在用这个端口，不会撞车）
       3. Playwright 截图验证关键帧（新增/改动的那几屏）
       4. render-video.sh 渲染成片
       5. 关 dev server
       6. 交付这一集
       7. 再处理下一集
```

**为什么音频合成也要收回主控**：即使 dev server 冲突能靠"subagent 不
起 server"绕开，本地 TTS 模型加载一次要几十秒、显存/内存吃满，**多个
subagent 同时喊它合成会排队甚至报错**——不如干脆只让主控一个人串行调用，
天然是个"锁"。

**给 subagent 的 prompt 必须显式列出"不允许做的事情"**，而不是只说"你
负责 XX"——正向描述职责范围，agent 仍可能"顺手"多做一步（起个 dev server
看看效果、跑一下音频听听），批量场景下这一步就是冲突源头。清单化写：
"不要起 dev server、不要跑 Playwright、不要跑音频合成、不要渲染视频、
不要 git commit"。

### 用任务列表追踪长链路

一集一集串行处理 20+ 集时，中途很容易断线（上下文压缩、被打断、临时插
其它任务）。用 `TaskCreate` 给每一集建一个任务（"E07 audio+render+deliver"
这种粒度），处理完立刻 `TaskUpdate` 标 `completed`——链路多长都不会丢步，
中途被打断也能靠任务列表状态知道下一步该处理哪一集。

## Part 3 · 内容一致性：让 subagent 抄现成的，不要各自发挥

批量改版最容易翻车的地方不是代码，是**内容**——27 个 subagent 各自去想
"这一集的三个知识点是什么""下一集叫什么名字"，答案质量参差、还可能编造。
两条规则堵住这个口子：

1. **本集的文案素材，指定读现成文件，不要临场编**。如果每集已经有一个
   "品牌封面"之类的静态展示组件（写死了标题 / 知识点摘要），批量新增的
   动态章节直接读它的常量复用，而不是让 subagent 重新概括一遍——省时间，
   还保证跟已发布的封面/简介文案不冲突。
2. **跨集才知道的信息（下一集是谁、系列进度），从系列级索引文件查，不要
   猜**。系列如果维护了一份选题清单（标题 / slug / 核心问题 一行一集），
   prompt 里直接告诉 subagent 去哪个文件查"下一行"，而不是让它去猜下一集
   叫什么。
3. **系列首尾集特殊处理，不能套统一模板**。批量任务的通用模板通常假设
   "还有下一集"，最后一集没有下一集，需要单独交代（收官感谢语 + 不出现
   "下一集见"字样）；如果系列有已归档（见 Part 5）的开头几集，批量任务
   的范围也要相应收窄。

## Part 4 · 不要推翻重写，先看现状再"保留 + 补"

系列做了很久，各集内部结构未必整齐——有的集已经有下一集预告，有的没有；
有的收尾是 2 步，有的是 5 步。批量 prompt 如果写"把最后一步换成 XXX"，
容易把已经写好的、比模板更丰富的内容也一起冲掉。

**给 subagent 的指令改成"先看现状，缺什么补什么"**：

- 让 subagent 自己打开对应文件看最后一步/预告步骤长什么样，而不是直接
  假设它是空的
- 已经存在、且方向正确的内容（比如已经有的下一集预告）**保留**，只在
  它缺失的字段（比如缺"核心问题"这一行）上**补全**
- 只有确认要被整体替换的内容（比如告别语要从"下一集见"换成新版感谢语）
  才明确写"替换成……"

批量跑下来会发现：不同集因为历史原因结构差异不小（同一个"收尾"章节，
有的叫 `ending`，有的步数不同，有的甚至藏着过时/错误的预告内容）——
subagent 在这种"半统一"现状里自主判断"保留什么、补什么"，比主控提前
把 27 集的现状全部翻一遍再写 27 份精确 diff 指令要划算得多。

## Part 5 · 系列里可能有归档集数，先探测再派工

系列做完的集数如果被打包成压缩包、原目录被删掉（省磁盘常见操作），批量
任务开始前**先探测哪些集是"活目录"**，只对活着的目录派 subagent：

```bash
for slug in "${ALL_EPISODES[@]}"; do
  [ -d "projects/<series>/$slug/app/presentation" ] && echo "$slug: 活" || echo "$slug: 已归档/不存在"
done
```

已归档的集数视为"已完稿定稿"，不在批量改版范围内（除非用户明确要求解压
改动）。这个探测步骤成本很低，但漏做的后果是对着不存在的目录发 subagent，
浪费一整轮 agent 调用还拿不到有效反馈。

## Part 6 · 语音多音字踩坑（本地 TTS 通用问题）

本地 TTS 遇到**单字多音字**、且文案里存在同一个字的高频"带偏"用法时，
容易统一读错音调。真实案例：某集脚本里"向量"（名词，量读四声 liàng）
出现频率很高，同一段文案里另一处"在量什么"（动词，量本该读二声 liáng）
被带偏读成了四声。

**规则**：批量写口播文案时，过一遍常见多音字清单（量 / 差 / 数 / 还 /
更 / 长 / 只 / 相 / 转 / 分 / 重 / 中……），凡是**单字孤立出现**且容易
被上下文带偏的，换成无歧义的双字词——比如"量"（动词"测量"义）单独出现
时换成"衡量"，"体量"这种名词搭配则保留。双字词几乎不会被本地 TTS 的
前端分词/多音字消歧模块读错，孤立单字才是重灾区。

**规则不是"排查完再验收"，是"写文案时就带着过一遍"**——批量场景下没人
会去逐段试听 27 集的音频找读音问题，等用户反馈了再回头改，成本比写的
时候多想一秒高得多。

## Part 7 · 情绪 / 语气调整：标点是唯一趁手的杠杆

本地 TTS 命令行工具通常**没有独立的情绪/语调参数**（temperature 之类的
采样参数只影响随机性，不是情绪）。用户要"这句话读得更兴奋一点"时，实际
能撬动的手段是：

- **标点**：陈述句改感叹号，是最直接影响韵律的信号
- **措辞**：把书面语换成更口语、更短促的表达（"感谢观看"→"感谢你看到
  这里！"）

改完标点/措辞后要**同步改屏幕上显示的文案**——不能口播文件带感叹号、
画面还是句号，两边一致，观众体感才对得上。

## Part 8 · 顺手发现的历史遗留 bug：记录，别跑题

批量处理时经常会碰到跟本次任务无关的老 bug——比如某一集的 Stage 组件
把横屏参数写成了竖屏项目的默认值，导致画面缩小错位。**发现了就顺手修**
（成本通常只有几行 diff），**但不要为了刨这个坑扩大任务范围**：

- 顺手修：当前正在编辑的文件里发现的、几行改动能修完的
- 不顺手修：需要额外调研/牵扯其它文件的，记下来告诉用户，留到下一轮

批量改版的 27/28 集体量下，这种历史 bug 冒出来的概率不低，主控自己也
要留意——渲染前的截图验证环节，除了看"这次改的新内容对不对"，也顺便
扫一眼整屏有没有明显的布局错位（内容飘到页面一角、比例不对），这类问题
大概率是与本次任务无关的老底子问题，但既然截图里看见了就一起修掉。

## Part 9 · Playwright 验证：够用就好，不用每屏都截

主控串行验证时，不需要把每一集新增的所有 step 都截图检查一遍——批量场景
下前几集验证充分后，同一套模板在其余集上出错的概率很低。实用做法：

- 前 2-3 集：完整截图（新增的每个 step + 改动的收尾），确认模板本身没问题
- 后续集：只截"信息密度最高/最容易出错"的一屏（通常是收尾那屏，因为
  文案是每集单独生成的，模板是复用的）——渲染前的这一步主要是防"文案
  塞不下换行乱了""下一集信息查错了"这类内容错误，不是防模板级布局错误
- 渲染出片后不需要逐秒重看，前面截图验证过就已经覆盖了主要风险

## 小结 Checklist

批量改版一个已有系列前，过一遍：

- [ ] 探测清楚哪些集是活目录（Part 5），范围只圈活着的
- [ ] 系列级索引文件（选题清单）在哪、字段有哪些，subagent prompt 里
      指名道姓告诉它去查
- [ ] 每集是否有现成的"文案素材源"（品牌封面常量之类）可以直接复用
- [ ] 收尾/首尾集要不要特殊处理（Part 3 第 3 条）
- [ ] subagent prompt 里明确列出"不允许做的事情"（不起 server / 不跑
      音频 / 不渲染 / 不 commit）
- [ ] 主控这边建好任务列表，一集一个任务，处理完立刻标记
- [ ] 音频合成 / dev server / 渲染三步，主控严格串行、一集处理完再下一集
- [ ] 文案过一遍多音字清单
- [ ] 如果用户要求"更兴奋/更XX"的语气，靠标点+措辞调，同步改屏幕文案
